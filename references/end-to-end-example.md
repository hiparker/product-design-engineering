# 从用户目标到可靠交付

设计同时涉及产品、界面和服务端时参考本例，以下为自行构造的演示场景，实际业务量、承诺和指标需要项目证据

## 场景与取舍

假设一个研究团队希望把已审核结论发给组织外的审阅者，目前需要人工复制结论并补上原始出处，用户提出“批量导出全部资料”

- 先核对接收者能否登录、是否要求离线审阅、是否必须固定版本、哪些原始材料允许对外提供
- 若证据支持离线与固定版本，首版可围绕“导出指定版本的已审核结论及允许提供的出处”完成一条交付任务
- 比较旧流程的准备时间与差错，以及新流程的选择、审核和学习成本，验证接受者是否仍需二次整理
- 区分操作者、审核人、接收者和系统管理员，明确谁可发起、谁可批准、谁可下载
- 用实际审阅任务检验价值，用原型检验选择范围和进度理解，用技术试验测量大文件处理，用数据范围与交付成本检验可持续性
- 记录任务完成率和准备时长的测量方式，同时关注错漏、越权与单位任务成本，目标值由当前基线和业务容忍度确定

## 定义界面与服务端共同遵守的契约

| 阶段 | 用户看见与能做什么 | 服务端保证什么 |
| --- | --- | --- |
| 选择 | 勾选结论，显示选择范围与导出内容 | 按当前权限提供可选对象 |
| 确认 | 查看固定版本与材料范围 | 受理时再校验权限、审核状态及版本 |
| 受理 | 获得任务入口，可离开页面 | 持久记录任务、发起人、范围、版本与请求身份 |
| 执行 | 显示排队或正在生成，可稍后回来 | 任务状态可查询，重启后可恢复或进入明确失败态 |
| 结果未知 | 保留原任务线索，提示正在确认结果 | 通过请求身份查询，安全重放复用原任务 |
| 完成 | 显示文件内容范围、生成时间与下载入口 | 结果完整可用后标记完成，下载时校验当前访问权 |
| 失败 | 解释可处理的原因，保留所选范围 | 记录失败阶段，按错误性质提供恢复动作 |
| 失效 | 显示文件已过期或访问权限改变 | 拒绝无效访问，重新生成时重新检查条件 |

若业务允许部分成功，结果应列明哪些内容缺失，下载文件也带有相同说明，若要求全量完整，则完整性校验通过后再开放下载

## 选择相称的实现

演示采用关系数据库保存任务，工作进程生成文件，对象存储保存结果，工作进程可先轮询任务表，按实际负载决定是否需要独立消息服务

- 受理请求在一个事务内保存任务及稳定的范围与版本引用，为租户、发起人和幂等键建立唯一约束，相同键的请求内容不一致时返回冲突
- 工作进程通过条件更新领取任务，带租约与执行批次标识，避免多个进程覆盖结果，失去租约的旧进程提交时被拒绝
- 为结果使用任务与执行批次对应的存储位置，先生成并校验文件，再以当前批次的条件更新标记完成，遗留文件由可重试的清理流程处理
- 记录选定的版本或一致快照，明确源数据后续修改的影响，避免长任务混入不同时间的内容
- 下载入口每次检查当前授权，若采用临时签名地址，明确有效期和撤销限制，并据业务要求选择代理下载或其他方案
- 成功通知作为附加动作单独记录发送结果，文件生成成功与通知到达分别呈现
- 当任务积压与交互请求争用资源时，再评估独立工作池、队列和存储扩容，以测量结果决定调整

## 从错误条件反查产品设计

| 注入的条件 | 要验证的结果 |
| --- | --- |
| 创建任务已提交，返回响应丢失 | 用户重试后获得同一任务，任务数量与副作用不增加 |
| 重复领取或执行进程失去租约 | 有效执行批次可以完成，旧批次无法覆盖已发布结果 |
| 文件生成后，更新任务状态失败 | 恢复后可以核对或重新生成，用户得到明确的可用文件 |
| 发起后撤销访问权 | 后续访问被拒绝，按业务契约重新检查执行权限 |
| 两人同时修改同一结论 | 版本冲突可识别，最终文件对应约定的有效版本 |
| 只有部分材料处理成功 | 文件与界面共同表达实际完成范围，满足所选完整性规则 |
| 任务超时且用户关闭页面 | 任务身份仍可查询，后续进入成功、失败或约定的恢复流程 |

这些验证同时检查产品承诺、可理解的反馈与数据一致性，技术错误暴露出业务语义缺失时，应回到范围和状态定义重新决策
