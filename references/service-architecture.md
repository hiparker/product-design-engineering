# 服务端架构决策

用于后端方案、前后端契约与可靠性设计，从当前代码、数据模型、调用链、部署约束和已有故障开始，选择能解释业务结果的方案

## 把业务承诺翻译成约束

| 产品承诺 | 需要明确的工程条件 |
| --- | --- |
| 保存后重新打开能看到 | 提交成功的时点、持久化与读取路径、缓存可见性 |
| 重试不会生成重复记录 | 请求身份、去重范围、保存期限与原子处理边界 |
| 只有指定成员可以读取 | 服务端授权、组织范围、授权撤销及后台任务的访问检查 |
| 导出可以稍后回来下载 | 持久任务、结果存储、查询接口、保留期限与失败恢复 |
| 多人修改能保留彼此工作 | 冲突检测、版本规则、合并或重提机制 |
| 关键操作可追溯 | 业务事件、操作者、对象版本、关联标识与记录保留规则 |

性能讨论使用实测或明确标注的假设，至少说明负载类型、峰值并发、请求或数据大小、读写比例、时延分位数和资源限制中与决策相关的项目

可用性目标说明测量窗口与成功定义，涉及恢复时确认允许丢失的数据量和恢复所需时间，再选择备份、恢复与冗余方案

## 先确定边界，再选择部署方式

- **列出数据归属与不变量**　确定谁负责修改对象，哪些字段必须一起变化，例如审核结果必须指向其实际审核过的结论版本
- **比较调用代价**　进程内模块边界便于统一事务和调试，独立服务增加网络失败、部署协调和观测成本，同时可获得独立扩缩容和故障隔离能力
- **用当前约束决定拆分**　已有系统延续可用边界，新系统可从职责清楚的单一部署开始评估，出现独立负载、发布节奏、权限隔离或团队责任需求时，再判断服务拆分的收益
- **写明重新评估的条件**　例如耗时导出已影响交互请求的时延、模块发布频繁互相阻塞，后续测量触及条件时调整边界

## 设计一条写入路径

- **定义请求契约**　说明对象标识、输入校验、授权、前置版本、业务错误和返回结果，异步接口返回可查询的任务身份与受理状态
- **在一致性边界内提交**　需要同时成立的本地变更放进事务，用约束或条件更新防止并发破坏不变量，明确隔离级别能覆盖哪些竞争情况
- **区分成功与结果未知**　响应丢失或超时后，调用方可能无法判断是否提交，用请求身份查询或安全重放获得确定结果，再向用户反馈
- **使幂等与副作用一起落地**　为业务请求定义作用域和唯一键，关联请求内容及结果，相同键配不同内容应被识别，避免先查不存在再无保护地写入
- **处理跨系统传播**　需要可靠异步传播时，可让本地业务修改与待发送事件在同一事务中提交，发送方允许重复投递，接收方将去重记录与业务修改放在可保证原子的边界内
- **说明不可原子覆盖的副作用**　外部通知或第三方操作优先使用对方的幂等能力，无法覆盖时给出可检测、可核对与可恢复的语义
- **选择跨服务一致性策略**　按业务允许的中间状态、资源预留和补偿能力比较方案，补偿可能需要新的业务动作，补偿失败要进入可恢复流程
- **为永久失败收尾**　重试有预算，超过条件后标记可识别状态并交给明确的恢复路径，确认中间数据如何保留及由谁处理

## 设计读取、缓存与性能

- 先观察慢查询、索引、扫描范围、连接和调用次数，再决定是否增加缓存或拆分服务
- 缓存写清权威来源、键的组织与权限范围、过期和失效方式，以及允许的陈旧窗口
- 更新成功后的界面需要读取新值时，采用返回新版本、读取权威存储或其他符合契约的方式保证可见性
- 对撤销授权等敏感变更明确缓存失效和再次授权的时点，避免旧权限继续用于访问
- 大列表使用稳定排序和合适的分页，排序键不唯一时加入唯一字段，说明翻页期间数据变化的行为
- 估计队列积压与单任务开销，限制大导出和批量任务对交互请求的资源争用，再以代表性负载验证

## 让依赖故障有边界

- **超时预算**　从端到端允许等待的时间分配下游调用预算，取消请求后明确后台工作是否继续
- **重试条件**　检查故障是否暂时、动作是否能安全重放、预算是否足够，采用退避与随机抖动，避免多层各自重试放大压力
- **隔离**　耗时任务与交互请求按资源消耗设置并发与队列边界，故障依赖可使用熔断降低持续压力
- **降级**　说明用户还能完成什么、哪些结果已陈旧或未完成，将失败传播到可理解的状态
- **限流**　明确限流范围、反馈与可恢复时间，大批量任务需要逐项处理结果或可追踪的任务状态

## 观测、演进与验证

- 对关键需求串起业务前提、页面状态、接口结果与持久化事实，例如“已受理”必须能按返回标识查询任务，接口测试与页面验证使用一致的状态定义
- 用任务或请求标识关联关键日志与调用过程，指标关注成功率、时延分位数、资源占用和队列等待等实际问题
- 日志记录定位问题所需的最小内容，避免凭证或整段敏感业务数据进入通用日志
- 修改持久化结构和接口时处理旧数据、新旧版本并存与后台积压任务，迁移按兼容方式分步执行
- 回退计划考虑已经写入的新数据、已执行的副作用和旧版本读取能力，恢复能力以实际验证为准
- 选择关键失败情形测试，例如提交后响应丢失、重复消息、并发写入、权限撤销、任务重启和部分处理失败

输出可简化为一张数据流图与若干决策说明，每个重要选择写清约束、采用方案、代价、失败恢复和重新评估条件，具体库版本与 API 在实施时核对当前官方文档
